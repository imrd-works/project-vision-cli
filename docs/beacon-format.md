# Формат зон и маяков

Спецификация модуля 0. Фиксирует решения, принятые при обсуждении 2026-10-03/04, и служит
контрактом для CLI, будущего сервера, дашборда и плагина редактора.

## Термины

| Термин        | Что это                                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Зона**      | Область продукта, за которую кто-то отвечает: «Вход и сессии», «Тарифы на главной». Сущность с ID, тегами, владельцем |
| **Маяк**      | Метка, указывающая на зону: в коде, в сообщении коммита, в карточке трекера                                           |
| **Карта зон** | Файл `.beacons/zones.yml` в репозитории: какие зоны есть и какие пути они покрывают                                   |
| **Тег**       | Тема аудита (`security`, `pci`, `a11y`). У зоны их может быть несколько, подзоны наследуют теги родителя              |
| **Регион**    | Фрагмент файла, размеченный маяком: его зона добавляется к зоне файла                                                 |

Зона — это **функциональность, а не папка**. Зоны известны из ТЗ раньше, чем появляется код, и
идут поперёк архитектурных слоёв: зона `auth.session` во фронтенде — это `pages/login`,
`features/login-form` и `entities/session`, а в бэкенде — `modules/auth`.

## ID зоны

Иерархический путь в структуре продукта, сегменты через точку, любой глубины:

```
home            home.hero           payments.checkout.card
```

- Сегмент: латиница в нижнем регистре, цифры и дефис, начинается с буквы — `^[a-z][a-z0-9-]*$`.
- `home.hero` — подзона `home`. Родителя объявлять не обязательно, но объявленный родитель
  передаёт подзонам свои теги.
- `none` и `completed` — зарезервированы и не могут быть ID зоны.
- ID общие на весь проект: одна и та же зона живёт в нескольких репозиториях под одним ID,
  каждый репозиторий описывает только свои пути.

## Карта зон: `.beacons/zones.yml`

```yaml
version: 1

zones:
  home:
    title: Главная страница
    paths: [src/pages/home/**]

  home.hero:
    title: Первый экран
    paths: [src/widgets/hero/**]

  home.pricing:
    title: Тарифы
    paths: [src/widgets/pricing/**]

  auth.session:
    title: Вход и сессии
    paths: [src/modules/auth/**]
    formerly: [auth.login]

  auth.passwords:
    title: Хранение паролей
    tags: [security]

  payments:
    title: Оплата
    tags: [security, pci]
    paths: [src/modules/payments/**]
```

| Поле          | Обязательно | Описание                                                                                   |
| ------------- | ----------- | ------------------------------------------------------------------------------------------ |
| `title`       | да          | Человекочитаемое название для дашборда и вывода CLI                                        |
| `description` | нет         | Что входит в зону, свободный текст                                                         |
| `paths`       | нет         | Glob-шаблоны от корня репозитория. Зона без путей и маяков — запланированная               |
| `tags`        | нет         | Темы аудита. Итоговые теги зоны = свои + теги всех объявленных предков                     |
| `formerly`    | нет         | Прежние ID зоны: коммиты со старым маяком засчитываются ей (историю git переписать нельзя) |

**Владельцев в карте нет.** Карта отвечает на вопрос «что есть в проекте», люди — «кто за это
отвечает». Владельцы, доверенные лица и гранты хранятся на сервере (модули 4, 6) и назначаются в
дашборде; клиент кеширует их для офлайн-проверок. В модулях 0–3 владельцев нет вообще.

**Даты в карте и маяках нет.** Когда зона или маяк появились, точно знает `git log`.

## Какой зоне принадлежит файл

1. **По карте.** Файл сопоставляется с `paths` всех зон.
   - Если подходят зоны из одной ветки иерархии (`home` и `home.hero`), побеждает самая глубокая.
   - Если подходят несвязанные зоны (`home.hero` и `payments`) — это ошибка карты: пересекающиеся
     пути почти всегда означают ошибку, и `beacon check` о ней сообщает.
2. **По маяку на файл.** Маяк в комментарии вне региона добавляет файл в зону целиком — так
   размечают файлы, которые лежат вне путей своей зоны.
3. **По региону.** Строки внутри региона дополнительно принадлежат зоне региона.

Итог: зоны файла = зона по карте + зоны маяков на файл; у строк региона — плюс зона региона.

Шапки во всех файлах зоны **не ставятся**: маяк в коде нужен только там, где карта файл не
покрывает (разбросанные файлы и регионы). Причина — шапки дублируют карту и расходятся с ней при
переименовании зоны, переносе папки и внедрении в существующий проект. Нейросеть узнаёт зону файла
командой `beacon which <файл>`, человек — в плагине редактора.

## Маяки в коде

Две равноправные формы, несколько зон через пробел:

```ts
// [BEACON: security.http]
// @beacon auth.session auth.passwords
```

```py
# @beacon payments.checkout
```

```html
<!-- [BEACON: home.hero] -->
```

```css
/* @beacon home.pricing */
```

Правила:

- Маяк распознаётся только в комментарии, который **начинает строку**, и только если текст
  комментария **начинается** с маяка: `// @beacon x` — маяк; `// см. @beacon x` и
  `foo() // @beacon x` — нет.
- Учитываются только настоящие комментарии языка файла: `//`, `/* */` — в C-подобных языках и
  CSS, `#` — в Python, YAML, shell, `--` — в SQL и Lua, `<!-- -->` — в HTML и Markdown (во Vue,
  Svelte и HTML ещё `//` и `/* */` встроенных скриптов). Для файлов неизвестного типа — любые
  из перечисленных.
- В Markdown строки внутри блоков кода (` ``` `, `~~~`) пропускаются: это примеры, а не разметка.
- В JSDoc-блоках `/** … */` маяк не распознаётся, чтобы не конфликтовать с JSDoc-инструментами
  (`eslint-plugin-jsdoc` и др.); `beacon check` подсказывает перенести его в обычный комментарий.
- С декораторами конфликта нет: маяк всегда внутри комментария.
- Маяк вне региона относится ко всему файлу, где бы в файле он ни стоял.

## Регионы

Построены на маркерах `#region` / `#endregion`, которые VS Code и другие редакторы уже умеют
сворачивать:

```ts
// #region @beacon security.http
await app.register(helmet, { … })
app.enableCors({ origin: config.cors.origins })
// #endregion
```

```ts
// #region [BEACON: home.hero]
…
// #endregion
```

- `#endregion` закрывает ближайший открытый регион; подпись после него необязательна.
- В языках с `#`-комментариями маркер пишется как `#region` или `# region`, в остальных —
  `// #region` (решётка обязательна, чтобы не путать с текстом вроде «region-specific»).
- Регионы могут быть вложенными. Обычные `#region` без маяка тоже участвуют в подсчёте
  вложенности, чтобы пары открытия и закрытия сопоставлялись так же, как в редакторе.
- Незакрытый регион и лишний `#endregion` — ошибки `beacon check`, если в файле есть регионы с
  маяками. Несбалансированные обычные регионы системы маяков не касаются.
- Зона региона **добавляется** к зонам файла, а не заменяет их.

## Маяки в коммитах

Только скобочная форма — в тексте коммита нет комментариев, скобки однозначно выделяют маяк:

```
feat(home): add yearly toggle to pricing [BEACON: home.pricing]

fix(auth): raise scrypt cost

[BEACON: auth.session] [BEACON: auth.passwords]
```

```
feat(home): pricing section done [BEACON: home.pricing completed]
```

Правила проверки коммита:

1. Затронутые зоны = зоны всех изменённых файлов + зоны регионов, внутрь которых попали
   изменённые строки.
2. Сообщение обязано содержать маяк **каждой** затронутой зоны — самой конкретной, без подмены
   родителем: правка в `home.hero` требует `[BEACON: home.hero]`, а не `[BEACON: home]`.
   Сводка вверх по иерархии — забота отчётов, а не автора коммита.
3. Маяк со старым ID из `formerly` засчитывается текущей зоне.
4. Маяк с неизвестным ID — ошибка (опечатка).
5. Лишние маяки (зона в карте есть, но коммит её не трогал) разрешены — например, `completed`
   отдельным коммитом.
6. Файлы вне всех зон коммитятся без маяков. Неразмеченный код не блокируется — систему можно
   внедрять постепенно.
7. Merge-коммиты не проверяются.

`completed` — флаг после ID: `[BEACON: <id> completed]`. Ставится сознательно, руками: в модуле 0
просто фиксирует финальный коммит по зоне, с модуля 3 закрывает пункты чекпоинта.

Маяки в сообщение **подставляет хук** `prepare-commit-msg`: разработчик открывает редактор
сообщения, а затронутые зоны уже вписаны. Хук `commit-msg` проверяет, что их не стёрли.

## Состояние зоны

Вычисляется, а не хранится — вручную заданное состояние неизбежно разойдётся с реальностью.

| Состояние     | Условие                                            |
| ------------- | -------------------------------------------------- |
| Запланирована | Нет путей с файлами и нет маяков в коде            |
| Активна       | Есть файлы по путям или маяки                      |
| Завершена     | В истории есть коммит с `[BEACON: <id> completed]` |

## Индекс

Команды `check`, `list` и `status` сканируют проект при каждом запуске — так индекс никогда не
устаревает — и сохраняют результат в `.git/beacon/index.json` для других инструментов: зоны с
итоговыми тегами и состоянием, файлы и диапазоны строк каждой зоны, покрытие, папки без зон,
ошибки разметки. Индекс лежит внутри папки git, а не в рабочем дереве: так он никогда не попадёт
в коммит и не попадётся форматтерам и линтерам, которые читают только корневые ignore-файлы.
Сканируются файлы, которые видит git (отслеживаемые и неигнорируемые новые), кроме бинарных
и крупнее 1 МБ. В модуле 1 индекс переезжает в SQLite с обновлением по изменению файлов.

## Команды CLI модуля 0

Все команды чтения поддерживают `--json` — на этом строятся плагин редактора и дашборд.

| Команда                             | Что делает                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| `beacon init`                       | Создаёт `.beacons/` с черновиком карты по структуре папок, подключает git-хуки |
| `beacon check [--with <repo>…]`     | Проверяет карту и разметку; `--with` сверяет ID зон с соседними репозиториями  |
| `beacon list [--tag t] [--zone id]` | Зоны и их файлы/диапазоны строк — то, что получает нейросеть на аудите         |
| `beacon which <файл>`               | Зоны файла (и регионов в нём)                                                  |
| `beacon status`                     | Покрытие кода зонами, неразмеченные папки, состояния зон                       |
| `beacon mark <файл> <зона>`         | Ставит маяк на файл в подходящем для языка комментарии                         |
| `beacon hook <имя> [аргументы git]` | Точки входа git-хуков: `prepare-commit-msg`, `commit-msg`, `pre-push`          |

`beacon init` в проекте с husky дописывает вызовы в `.husky/*`, а не перезаписывает хуки; без
husky — ставит хуки в `.git/hooks`. Хук `pre-push` перепроверяет весь пушимый диапазон — на
случай коммитов через `--no-verify`.

## Несколько репозиториев

До модуля 4 у каждого репозитория своя карта, ID зон согласуются вручную;
`beacon check --with ../frontend` показывает зоны, которые есть только с одной стороны. С модуля 4
общий список зон хранит сервер: архитектор заводит зону один раз, репозитории дают только пути.

## Что не входит в модуль 0

- Владельцы, доверенности, гранты, gate-check агента — модули 6–7.
- Шапки во всех файлах зоны (`beacon sync`) — опция, появится по запросу.
- Подсказки нейросети для неразмеченных файлов при `init`.
- Плагин редактора — после модуля 1 (см. план).
