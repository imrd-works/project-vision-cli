# Формат зон и маяков

Спецификация модуля 0. Фиксирует решения, принятые при обсуждении 2026-10-03/04, и служит
контрактом для CLI, будущего сервера, дашборда и плагина редактора.

## Термины

| Термин        | Что это                                                                                                               |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Зона**      | Область продукта, за которую кто-то отвечает: «Вход и сессии», «Тарифы на главной». Сущность с ID, тегами, владельцем |
| **Маяк**      | Метка, указывающая на зону: в коде, в сообщении коммита, в карточке трекера                                           |
| **Карта зон** | Файл `.beacons/zones.yml` в репозитории: какие зоны есть и какие пути они покрывают                                   |
| **Тег**       | Тема аудита (`security`, `pci`, `a11y`). У зоны их может быть несколько, подзоны наследуют теги родителя              |
| **Регион**    | Фрагмент файла, размеченный маяком: его зона добавляется к зоне файла                                                 |

Зона — это **функциональность, а не папка**. Зоны известны из ТЗ раньше, чем появляется код, и
идут поперёк архитектурных слоёв: зона `auth.session` во фронтенде — это `pages/login`,
`features/login-form` и `entities/session`, а в бэкенде — `modules/auth`.

## ID зоны

Иерархический путь в структуре продукта, сегменты через точку, любой глубины:

```
home            home.hero           payments.checkout.card
```

- Сегмент: латиница в нижнем регистре, цифры и дефис, начинается с буквы — `^[a-z][a-z0-9-]*$`.
- `home.hero` — подзона `home`. Родителя объявлять не обязательно, но объявленный родитель
  передаёт подзонам свои теги.
- `none` и `completed` — зарезервированы и не могут быть ID зоны.
- ID общие на весь проект: одна и та же зона живёт в нескольких репозиториях под одним ID,
  каждый репозиторий описывает только свои пути.

## Карта зон: `.beacons/zones.yml`

```yaml
version: 1

zones:
  home:
    title: Главная страница
    paths: [src/pages/home/**]

  home.hero:
    title: Первый экран
    paths: [src/widgets/hero/**]

  home.pricing:
    title: Тарифы
    paths: [src/widgets/pricing/**]

  auth.session:
    title: Вход и сессии
    paths: [src/modules/auth/**]
    formerly: [auth.login]

  auth.passwords:
    title: Хранение паролей
    tags: [security]

  payments:
    title: Оплата
    tags: [security, pci]
    paths: [src/modules/payments/**]
```

| Поле          | Обязательно | Описание                                                                                   |
| ------------- | ----------- | ------------------------------------------------------------------------------------------ |
| `title`       | да          | Человекочитаемое название для дашборда и вывода CLI                                        |
| `description` | нет         | Что входит в зону, свободный текст                                                         |
| `paths`       | нет         | Glob-шаблоны от корня репозитория. Зона без путей и маяков — запланированная               |
| `tags`        | нет         | Темы аудита. Итоговые теги зоны = свои + теги всех объявленных предков                     |
| `formerly`    | нет         | Прежние ID зоны: коммиты со старым маяком засчитываются ей (историю git переписать нельзя) |

**Владельцев в карте нет.** Карта отвечает на вопрос «что есть в проекте», люди — «кто за это
отвечает». Владельцы, доверенные лица и гранты хранятся на сервере (модули 4, 6) и назначаются в
дашборде; клиент кеширует их для офлайн-проверок. В модулях 0–3 владельцев нет вообще.

**Даты в карте и маяках нет.** Когда зона или маяк появились, точно знает `git log`.

## Какой зоне принадлежит файл

1. **По карте.** Файл сопоставляется с `paths` всех зон.
   - Если подходят зоны из одной ветки иерархии (`home` и `home.hero`), побеждает самая глубокая.
   - Если подходят несвязанные зоны (`home.hero` и `payments`) — это ошибка карты: пересекающиеся
     пути почти всегда означают ошибку, и `beacon check` о ней сообщает.
2. **По маяку на файл.** Маяк в комментарии вне региона добавляет файл в зону целиком — так
   размечают файлы, которые лежат вне путей своей зоны.
3. **По региону.** Строки внутри региона дополнительно принадлежат зоне региона.

Итог: зоны файла = зона по карте + зоны маяков на файл; у строк региона — плюс зона региона.

Шапки во всех файлах зоны **не ставятся**: маяк в коде нужен только там, где карта файл не
покрывает (разбросанные файлы и регионы). Причина — шапки дублируют карту и расходятся с ней при
переименовании зоны, переносе папки и внедрении в существующий проект. Нейросеть узнаёт зону файла
командой `beacon which <файл>`, человек — в плагине редактора.

## Маяки в коде

Две равноправные формы, несколько зон через пробел:

```ts
// [BEACON: security.http]
// @beacon auth.session auth.passwords
```

```py
# @beacon payments.checkout
```

```html
<!-- [BEACON: home.hero] -->
```

```css
/* @beacon home.pricing */
```

Правила:

- Маяк распознаётся только в комментарии, который **начинает строку**, и только если текст
  комментария **начинается** с маяка: `// @beacon x` — маяк; `// см. @beacon x` и
  `foo() // @beacon x` — нет.
- Учитываются только настоящие комментарии языка файла: `//`, `/* */` — в C-подобных языках и
  CSS, `#` — в Python, YAML, shell, `--` — в SQL и Lua, `<!-- -->` — в HTML и Markdown (во Vue,
  Svelte и HTML ещё `//` и `/* */` встроенных скриптов). Для файлов неизвестного типа — любые
  из перечисленных.
- В Markdown строки внутри блоков кода (` ``` `, `~~~`) пропускаются: это примеры, а не разметка.
- В JSDoc-блоках `/** … */` маяк не распознаётся, чтобы не конфликтовать с JSDoc-инструментами
  (`eslint-plugin-jsdoc` и др.); `beacon check` подсказывает перенести его в обычный комментарий.
- С декораторами конфликта нет: маяк всегда внутри комментария.
- Маяк вне региона относится ко всему файлу, где бы в файле он ни стоял.

## Регионы

Построены на маркерах `#region` / `#endregion`, которые VS Code и другие редакторы уже умеют
сворачивать:

```ts
// #region @beacon security.http
await app.register(helmet, { … })
app.enableCors({ origin: config.cors.origins })
// #endregion
```

```ts
// #region [BEACON: home.hero]
…
// #endregion
```

- `#endregion` закрывает ближайший открытый регион; подпись после него необязательна.
- В языках с `#`-комментариями маркер пишется как `#region` или `# region`, в остальных —
  `// #region` (решётка обязательна, чтобы не путать с текстом вроде «region-specific»).
- Регионы могут быть вложенными. Обычные `#region` без маяка тоже участвуют в подсчёте
  вложенности, чтобы пары открытия и закрытия сопоставлялись так же, как в редакторе.
- Незакрытый регион и лишний `#endregion` — ошибки `beacon check`, если в файле есть регионы с
  маяками. Несбалансированные обычные регионы системы маяков не касаются.
- Зона региона **добавляется** к зонам файла, а не заменяет их.

## Маяки в коммитах

Только скобочная форма — в тексте коммита нет комментариев, скобки однозначно выделяют маяк:

```
feat(home): add yearly toggle to pricing [BEACON: home.pricing]

fix(auth): raise scrypt cost

[BEACON: auth.session] [BEACON: auth.passwords]
```

```
feat(home): pricing section done [BEACON: home.pricing completed]
```

Правила проверки коммита:

1. Затронутые зоны = зоны всех изменённых файлов + зоны регионов, внутрь которых попали
   изменённые строки.
2. Сообщение обязано содержать маяк **каждой** затронутой зоны — самой конкретной, без подмены
   родителем: правка в `home.hero` требует `[BEACON: home.hero]`, а не `[BEACON: home]`.
   Сводка вверх по иерархии — забота отчётов, а не автора коммита.
3. Маяк со старым ID из `formerly` засчитывается текущей зоне.
4. Маяк с неизвестным ID — ошибка (опечатка).
5. Лишние маяки (зона в карте есть, но коммит её не трогал) разрешены — например, `completed`
   отдельным коммитом.
6. Файлы вне всех зон коммитятся без маяков. Неразмеченный код не блокируется — систему можно
   внедрять постепенно.
7. Merge-коммиты не проверяются.

`completed` — флаг после ID: `[BEACON: <id> completed]`. Ставится сознательно, руками: в модуле 0
просто фиксирует финальный коммит по зоне, с модуля 3 закрывает пункты чекпоинта.

Маяки в сообщение **подставляет хук** `prepare-commit-msg`: разработчик открывает редактор
сообщения, а затронутые зоны уже вписаны. Хук `commit-msg` проверяет, что их не стёрли.

## Карточки трекеров

Карточка Jira, ClickUp или другого трекера связывается с зоной тем же маяком в квадратных
скобках — в названии или описании, без кастомных полей трекера. Слово рядом с зоной говорит,
чем карточка приходится чекпоинту:

| Маяк в карточке                  | Что это                                                         |
| -------------------------------- | --------------------------------------------------------------- |
| `[BEACON: auth.session]`         | задача по зоне                                                  |
| `[BEACON: auth.session stopper]` | стопер: чекпоинт с этой зоной не закрыть, пока карточка открыта |
| `[BEACON: auth.session debt]`    | техдолг зоны                                                    |

Сервер команды получает карточки вебхуками трекеров, находит по зоне её владельца и чекпоинты,
где она — пункт, и показывает карточку там же. В git ничего не пишется: закрытие карточки в
трекере закрывает связь. После `beacon sync` карточки видны в `beacon checkpoints --team`, а
карточки ваших зон — в `beacon todo --team`. Библиотека отдаёт разбор — `parseCardBeacons(text)`.

## Тестировщики

Тест-кейсы и баг-репорты живут на сервере команды: тестировщику не нужен доступ к git. После
`beacon sync` `beacon checkpoints --team` показывает под чекпоинтом, сколько тест-кейсов
пройдено, и незакрытые баги; `beacon todo --team` — разработчику открытые баги его зон,
тестировщику — чекпоинты, готовые к проверке, и исправления, которые ждут его подтверждения.

Баг не останавливает работу, но чекпоинт без условий не закрыть, пока тест-кейсы не пройдены
и баги не подтверждены закрытыми: `beacon checkpoint close` назовёт, что осталось. Условное
закрытие (`--conditional` с техдолгом) остаётся.

## Состояние зоны

Вычисляется, а не хранится — вручную заданное состояние неизбежно разойдётся с реальностью.

| Состояние     | Условие                                            |
| ------------- | -------------------------------------------------- |
| Запланирована | Нет путей с файлами и нет маяков в коде            |
| Активна       | Есть файлы по путям или маяки                      |
| Завершена     | В истории есть коммит с `[BEACON: <id> completed]` |

## Индекс

Индекс — разобранная разметка каждого файла, который видит git (отслеживаемые и неигнорируемые
новые), кроме бинарных и крупнее 1 МБ. Он хранится в SQLite: `.git/beacon/index.db` — внутри папки
git, поэтому никогда не попадает в коммит и не мешает форматтерам и линтерам. Файл перечитывается,
только если изменились его размер или время изменения; файлы, изменённые прямо во время скана,
перепроверяются в следующий раз (та же защита, что у самого git). Смена правил разбора сбрасывает
кеш целиком.

Команды `check`, `list`, `status`, `audit` обновляют индекс при каждом запуске — он никогда не
устаревает. `beacon watch` и `beacon serve` держат его актуальным непрерывно: следят за файлами и
за журналом коммитов (состояние «завершена»).

## Проверка архитектуры

Архитектурные правила (FSD, слои, границы модулей) проверяет инструмент, который уже есть в
проекте, — beacon их не дублирует, а запускает и показывает. Что запускать, задаёт необязательный
`.beacons/config.yml`; `beacon init` создаёт его сам, если найдёт в зависимостях проекта
`eslint-plugin-boundaries`, `steiger` или `dependency-cruiser`.

```yaml
version: 1

validation:
  - tool: eslint # команда и правила — по умолчанию для инструмента
  - name: fsd
    tool: steiger
    command: npx --no steiger src --reporter json
    rules: [fsd/*]

dynamics:
  gapDays: 3

techDebt:
  limitPerDeveloper: 2 # открытых долгов на человека; сверх — коммиты только в зоны долгов
  extendDays: 7 # шаг автопродления просроченного долга

stagnation:
  days: 3 # рабочих дней без коммитов в своих зонах до «застоя»
identity: # кто делает коммит — см. «Люди и авторы коммитов»
  check: email # signature | email | off
  staleDays: 7
  whenStale: allow # hold — не коммитить на устаревших данных
server: # сервер команды для beacon sync (необязательно)
  url: https://vision.example.com
  project: 54cc4d32-7588-4252-a186-832699730b5a
```

| Инструмент           | Команда по умолчанию                        | Правила по умолчанию                                   |
| -------------------- | ------------------------------------------- | ------------------------------------------------------ |
| `eslint`             | `npx --no eslint . --format json`           | `boundaries/*`, `import/no-cycle`, `import-x/no-cycle` |
| `steiger`            | `npx --no steiger src --reporter json`      | все                                                    |
| `dependency-cruiser` | `npx --no depcruise src --output-type json` | все                                                    |

- `rules` — glob-шаблоны ID правил, которые считаются архитектурными: ESLint проверяет и стиль, а
  в отчёт попадают только они.
- Нарушения привязываются к зонам файлов — видно, чья архитектура нарушена.
- Статус проверки: «пройдена» (ошибок нет, предупреждения допустимы), «нарушения» (есть ошибки),
  «ошибка» (инструмент не выдал отчёт — не установлен, упал, неверная команда).
- `beacon validate` — разовая проверка, код выхода 1 при нарушениях (годится для CI).
  `beacon watch` и `beacon serve` перезапускают проверки после изменений файлов, по одной за раз.

## Дерево архитектуры и история

**Дерево архитектуры** — папки проекта с числом файлов, сколько из них в зонах и какие зоны в них
лежат. Входит в индекс и обновляется вместе с ним: новая папка появляется в дереве сама.
`beacon tree [--depth n]` печатает его текстом; нейросеть на аудите сверяет структуру с ним
(MCP: `architecture_tree`), а не обходит файловую систему.

**История** — `beacon history`: последние 5000 коммитов без merge-коммитов, сгруппированные по
зонам из их маяков (с учётом `formerly`): сколько коммитов, кто их автор, последний коммит.

**Динамика** — по дням, от первого коммита с маяком до сегодня: коммиты в зонах и накопленное
число завершённых зон. **Провал** — серия из `gapDays` и более рабочих дней (пн–пт) без коммитов в
зонах; выходные её не прерывают и не удлиняют. С модуля 3 к провалам добавится причина из техдолга.

## Чекпоинты

`.beacons/checkpoints.yml` — план архитектора для линии этого репозитория (фронтенд, бэкенд,
DevOps): чекпоинты с обязательными пунктами и связями, и решения по ним — ручные галочки,
закрытия, техдолг. Файл живёт в git: план ревьюят в PR, решения доходят до команды коммитом
(с модуля 4 их будет хранить сервер).

```yaml
version: 1
line: frontend # ID линии; другие линии ссылаются на её чекпоинты как frontend:<id>
title: Фронтенд

checkpoints:
  ui-kit:
    title: UI-кит
    deadline: 2026-10-20
    items:
      - zone: ui.button # закрывается сам: зона завершена, архитектура в ней чистая
        owner: ann@company.com
      - id: design # ручной пункт: beacon checkpoint tick ui-kit design
        check: Согласован с дизайнером

  auth-pages:
    title: Страницы входа
    after: [ui-kit] # порядок на линии
    dependsOn: [backend:auth-api] # связь с точкой другой линии
    items:
      - zone: auth.login-page
```

**Пункты.** Пункт-зона закрывается сам, когда зона завершена (`[BEACON: id completed]`) и в её
файлах нет нарушений архитектуры. Ручной пункт отмечает `beacon checkpoint tick` — в файл
записываются дата и кто отметил.

**Состояния** вычисляются: «открыт» → «готов к аудиту» (все пункты закрыты, см. «Кросс-аудит»)
→ «закрыт». Закрытие подтверждает `beacon checkpoint close`; с незакрытыми пунктами — только
условно.

**Условное закрытие и техдолг.** `beacon checkpoint close <id> --conditional --reason «…»
--deadline ГГГГ-ММ-ДД [--owner email] [--waits-for линия:чекпоинт] [--zones a,b]` закрывает
чекпоинт особым состоянием и обязательно создаёт техдолг: причина, владелец, дедлайн, зоны
недоделанного (по умолчанию — зоны незакрытых пунктов). Просроченный долг краснеет и
автоматически продлевается на `techDebt.extendDays` дней — продление вычисляется от исходного
дедлайна, файл не переписывается. `beacon debt close` закрывает долг.

**Связи и стоперы.** `dependsOn` связывает чекпоинт с точкой другой линии. Чекпоинт, который ждут
незакрытые чекпоинты или открытые долги, — **стопер**. Линии разных репозиториев видят друг друга
через `--with` (`beacon checkpoints --with ../backend`, `beacon serve --with ../frontend`): каждый
репозиторий — одна линия; с модуля 4 это заменит сервер.

**Приоритетный захват.** Долг с `waitsFor` ждёт чекпоинт; как только тот закрыт, долг становится
первым в личном списке владельца — `beacon todo`.

**Лимит техдолга.** Разработчик с открытыми долгами сверх `techDebt.limitPerDeveloper` может
коммитить только в зоны своих долгов — хук `commit-msg` отклоняет остальное: сначала долг.
Аварийно — `[DEBT-OVERRIDE: причина]` в сообщении, причина остаётся в истории. Лимит
персональный: блокируется только тот, у кого он превышен.

**Застой.** Владелец незакрытого пункта или открытого долга, который не коммитит в свои зоны
дольше порога, — застрял. Порог — `stagnation.days` рабочих дней, но не меньше удвоенной медианы
времени, за которое в проекте завершались зоны (когда завершённых зон набралось от пяти).

**Разработчик** до модуля 6 — git-идентичность: `owner` — email из `git config user.email`. С
модуля 6 email привяжется к человеку через OAuth.

## Кросс-аудит

Когда все пункты чекпоинта закрыты, команда проверяет его целиком — каждый разработчик своей
нейросетью: то, что упустила одна модель, заметит другая. Раунды повторяются, пока каждый
аудитор не подпишется под текущим состоянием.

```yaml
checkpoints:
  auth-api:
    title: API входа
    items: [...]
    audit: # необязательно: по умолчанию аудиторы — владельцы пунктов
      auditors: [ann@company.com, bob@company.com]
      consolidator: bob@company.com # сводит находки; по умолчанию — кто начал раунд
```

1. `beacon audit start <чп>` открывает раунд на сервере команды на текущем коммите линии.
2. Каждый аудитор: `beacon audit report <чп> [--model …]` создаёт его отчёт
   `.beacons/audits/<чп>/round-<n>/<почта>.md`; код зон чекпоинта для модели —
   `beacon audit --checkpoint <чп>` или MCP-инструмент `audit_checkpoint`. Отчёт коммитится.
3. Сводящий: `beacon audit merge <чп>` показывает все находки раунда по файлам и создаёт
   `summary.md`, где каждой находке ставится решение — `[fixed]`, `[disputed]` или
   `[accepted]`, — и вносит исправления.
4. `beacon sign <чп> agree | accept-risk | object [--comment …]`: подпись под раундом. Принятый
   риск и возражение объясняются комментарием. Возражение — нужен следующий раунд по
   исправленной версии.

Отчёт — Markdown с заголовком; каждая находка — заголовок `### [важность]` (`critical`, `high`,
`medium`, `low`, `info`) со строками `- Файл: путь:строка` и `- Зона: id`:

```markdown
---
checkpoint: backend:auth-api
round: 1
author: ann@company.com
model: claude-opus-5-5
commit: 1a2b3c4
---

## Находки

### [high] Пароль сравнивается без постоянного времени

- Файл: src/auth/password.service.ts:42
- Зона: auth.passwords

Что не так, чем грозит, как исправить.
```

Отчёты и сводки живут в git — их видно в PR и на сервере (по зеркалу). Раунды и подписи —
общая истина сервера: подпись привязана к раунду и его коммиту, ставится только за себя, а
сделанная офлайн под уже сменившимся раундом становится конфликтом, который решает человек.
Аудит пройден, когда все аудиторы последнего раунда подписали «согласен» или «принимаю риск».
Закрыть чекпоинт без пройденного аудита можно (закрытие — это коммит, оно работает офлайн), но
он будет отмечен «закрыт без кросс-аудита».

## Аудит нейросетью

Нейросеть получает код темы, не перечитывая репозиторий, двумя способами.

**Пакет контекста** — `beacon audit --tag security` (или `--zone auth`): один Markdown-документ
с таблицей зон, полным кодом их файлов (до 400 строк на файл) и фрагментами регионов с тремя
строками контекста. Файл, входящий в несколько зон, приводится один раз. Тесты по умолчанию
исключены (`--tests` — включить), `--no-code` — только пути и диапазоны строк. Пакет можно
сохранить в файл или передать любой модели.

**MCP-сервер** — `beacon mcp` (stdio) для агентов вроде Claude Code и Cursor. Инструменты:

| Инструмент              | Что возвращает                                                       |
| ----------------------- | -------------------------------------------------------------------- |
| `list_zones`            | Зоны по тегу или ветке зоны: теги, состояние, файлы, диапазоны строк |
| `which_zone`            | Зоны файла и регионов в нём                                          |
| `audit_context`         | Пакет контекста, как `beacon audit`                                  |
| `zone_status`           | Покрытие, состояния зон, папки без зон                               |
| `architecture_tree`     | Дерево архитектуры текстом                                           |
| `validate_architecture` | Запускает проверки архитектуры, нарушения с зонами                   |
| `checkpoints`           | Линии чекпоинтов с прогрессом, стоперами, техдолгом и застоем        |
| `todo`                  | Личный список разработчика                                           |

`beacon init` добавляет в `AGENTS.md` короткие правила для агентов: узнавать зону перед правкой,
брать код темы через `audit`/MCP, размечать новые файлы, не удалять маяки из коммитов.

## Локальный API

`beacon serve` поднимает HTTP API только для чтения поверх живого индекса — источник данных
дашборда: открытый локальный клиент отдаёт данные, закрытый интерфейс их показывает.

| Запрос                        | Ответ                                                                             |
| ----------------------------- | --------------------------------------------------------------------------------- |
| `GET /api/index`              | Проект, версия индекса, зоны, файлы, покрытие, проблемы                           |
| `GET /api/events`             | Server-Sent Events: `index` с новой версией при каждом изменении                  |
| `GET /api/which?file=…`       | Зоны файла                                                                        |
| `GET /api/audit?tag=…&zone=…` | Пакет контекста (`tests=1` — с тестами, `code=0` — без кода)                      |
| `GET /api/history`            | Коммиты по зонам и динамика                                                       |
| `GET /api/validation`         | Последние результаты проверок архитектуры; SSE `validation` после каждого прогона |
| `GET /api/timeline`           | Линии чекпоинтов этого и `--with`-репозиториев: пункты, стоперы, техдолг, застой  |
| `GET /api/todo?owner=…`       | Личный список: техдолг (приоритетный первым) и незакрытые пункты                  |
| `GET /api/registry`           | Правила архитектора и исключения из них (рабочая копия)                           |

API отдаёт исходный код, поэтому по умолчанию слушает только `127.0.0.1:4317`, отвечает только
на локальные имена хоста (защита от DNS rebinding) и только браузерным origin из списка
(`--origin`, по умолчанию `http://localhost:5173` — дашборд в разработке).

## Сервер команды

Сервер держит общую истину команды: зеркала репозиториев проекта, по каждой ветке — снимок, и
состояние, которого нет в git: заметки к чекпоинтам, подписи аудита, люди и владельцы зон.
Репозиторий узнаёт свой сервер и проект из `.beacons/config.yml`:

```yaml
server:
  url: https://vision.example.com
  project: 54cc4d32-7588-4252-a186-832699730b5a # id проекта из дашборда
```

| Команда                          | Что делает                                                                |
| -------------------------------- | ------------------------------------------------------------------------- |
| `beacon login [<сервер>]`        | Открывает дашборд, вы подтверждаете вход (сверив код), CLI получает токен |
| `beacon logout [<сервер>]`       | Забывает токен сервера                                                    |
| `beacon sync`                    | Отправляет изменения, сделанные офлайн, и забирает состояние проекта      |
| `beacon note <линия:чп> <текст>` | Заметка к чекпоинту для всей команды; `--delete` — удалить                |
| `beacon checkpoints --team`      | Все линии проекта (все репозитории) с заметками — по данным сервера       |
| `beacon todo --team`             | Мой список по всему проекту — по данным сервера                           |
| `beacon whoami`                  | Кто я в проекте: аккаунт, автор коммитов, подпись, мои зоны, контакты     |
| `beacon owners [<зона>]`         | Владельцы зон и доверенные лица, по именам                                |
| `beacon signing setup [--key f]` | Подписывать коммиты этого репозитория SSH-ключом                          |
| `beacon grant`, `beacon grants`  | Гранты на правку логики зоны (владелец зоны или проекта)                  |
| `beacon exception approve <id>`  | Одобрить или отклонить исключение                                         |

Вход устроен как у Sanity Studio: токен приходит в CLI только после подтверждения в браузере,
хранится в папке настроек пользователя (`~/.config/beacon/credentials.json`, права 600;
`BEACON_CONFIG_DIR` — другая папка) и отзывается в дашборде.

**Офлайн.** `beacon sync` кладёт состояние проекта в `.git/beacon/sync.json`; без сети
`--team`-команды показывают его с датой. Изменения, сделанные офлайн (`beacon note`), ждут в той
же папке и уходят при следующем `beacon sync`: сервер применяет каждое ровно один раз, даже если
ответ потерялся и CLI отправил его снова. Как сливаются одновременные изменения, решает вид
сущности: для заметок побеждает сделанное позже (по времени изменения, а не отправки), для
критичных вещей — подписей, решений по чекпоинтам — изменение поверх устаревшей версии
становится конфликтом, его решает человек.

Всё, что лежит в git (`.beacons/*`, маяки, план чекпоинтов), синхронизируется самим git: сервер
узнаёт о push по вебхуку и пересчитывает снимок ветки. Два разных закрытия одного чекпоинта —
это конфликт слияния в `checkpoints.yml`, и решается он как любой конфликт в git.

### Люди и авторы коммитов

Владелец зоны — человек с настоящими именем и фамилией, его аккаунт GitHub или GitLab привязан в
профиле дашборда через OAuth. Владельцев и доверенных лиц зон назначает владелец проекта в
дашборде: маяки в коде несут только ID зоны. `beacon sync` приносит людей, владельцев и ключи
подписи привязанных аккаунтов и кладёт ключи в `.git/beacon/allowed_signers` — файл
`gpg.ssh.allowedSignersFile` для git.

Поле автора в коммите вписывает кто угодно, поэтому хуки проверяют автора по `identity.check`:

| Значение    | `commit-msg` (до коммита)                                     | `pre-push` (сделанные коммиты)                 |
| ----------- | ------------------------------------------------------------- | ---------------------------------------------- |
| `email`     | почта автора — почта участника проекта                        | автор каждого коммита — участник проекта       |
| `signature` | плюс: коммит подписывается SSH-ключом аккаунта этого человека | каждый коммит подписан ключом своего же автора |
| `off`       | без проверки                                                  | без проверки                                   |

Подпись чужим ключом — даже ключом другого участника — не подтверждает автора. Подписывать
коммиты: `beacon signing setup` (ключ из `~/.ssh` или `--key`), сам ключ добавляется на GitHub
или GitLab как ключ подписи (Signing Key) и подтягивается кнопкой «Обновить ключи» в профиле.

Проверка работает офлайн, по данным последнего `beacon sync`. Данные старше `staleDays` дней
(или их нет вовсе) при `whenStale: allow` только дают предупреждение, при `hold` — не пускают
коммит до `beacon sync`. Без `server` в настройках проверки нет.

## Ownership

Владельцы зон и доверенные лица назначаются на сервере (см. «Люди и авторы коммитов»). Право на
правку зависит от её типа:

| Правка                                   | Кто может                                              |
| ---------------------------------------- | ------------------------------------------------------ |
| Логика, структура, сигнатуры             | Владелец зоны, доверенное лицо или по гранту владельца |
| Тексты, комментарии, форматирование      | Любой                                                  |
| Использование чужого компонента как есть | Любой — его файлы не меняются                          |
| Внутренняя логика чужого компонента      | Через владельца                                        |

Косметика определяется по диффу: если после удаления комментариев, содержимого строк и пробелов
код файла не изменился — это косметика; тексты (`*.md`), переводы (`locales/`, `i18n/`) и стили
— тоже. Владелец родительской зоны отвечает за подзону, пока у той нет своего. У зоны без
владельца ограничений нет.

**Гранты.** Владелец зоны или проекта разрешает человеку менять логику зоны — до даты или
бессрочно: `beacon grant auth bob@x.io --until 2026-10-12 --reason "…"`, отозвать —
`beacon grant revoke auth bob@x.io`. Грант действует и на подзоны. Коммит, сделанный по гранту,
получает маяк-разрешение — строку `Beacon-Grant: auth for bob@x.io by ann@x.io until 2026-10-12`.

**Два рубежа.** До правки: `beacon gate <файлы>`, MCP-инструмент `gate_check` и хук Claude Code,
который ставит `beacon init --agent-hooks`: он видит правку агента до записи и запрещает правку
логики чужой зоны, называя владельца и его контакты. На коммите: `commit-msg` проверяет
подготовленные изменения, `pre-push` — каждый пушимый коммит. Всё работает офлайн по данным
последнего `beacon sync`; репозиторий проекта определяется по адресу `origin`, иначе —
`server.repository` в настройках.

```yaml
ownership:
  enforce: block # block — не пускать; warn — предупредить; off — не проверять
```

## Правила и исключения

Архитектор описывает обязательные условия реализации в `.beacons/rules.yml`:

```yaml
version: 1
rules:
  fsd-layers:
    title: Слои FSD
    kind: architecture # architecture | api | naming | other
    description: Импорты — только в нижележащие слои
    zones: [web] # без zones — весь репозиторий
    validatorRules: [boundaries/*] # правила валидаторов, которые это проверяют
  ui-names:
    title: Компоненты — PascalCase
    kind: naming
    naming:
      - paths: ['src/**/ui/*.tsx']
        pattern: ^[A-Z]
```

Осознанное отклонение — именная запись в `.beacons/exceptions.yml`, рядом с кодом и маяками:

```yaml
version: 1
exceptions:
  - id: legacy-profile
    rule: fsd-layers
    zones: [web.profile] # или paths: [glob]
    reason: Старый профиль импортирует виджет, пока его не перепишут
    raw: ну там старый профиль, перепишем потом # исходные слова, если текст правил ассистент
    author: bob@example.com
    date: 2026-10-05
    checkpoint: frontend:profile
```

- `beacon exception add --rule … --zones … --reason "…"` дописывает запись; ИИ-агент делает
  то же MCP-инструментом `record_exception`, переписав объяснение разработчика начисто и передав
  его исходные слова в `raw`.
- Кто разрешил — решает сервер, а не файл: `beacon exception approve <id>` (или `--reject`)
  доступно владельцу зоны и владельцу проекта; решение видно в `beacon exceptions` и дашборде.
- `beacon check` проверяет имена файлов по правилам `naming`; `beacon validate` считает
  нарушения валидаторов, покрытые исключением, осознанным отклонением, а не ошибкой.
- Пакет аудита (`beacon audit`, `audit_checkpoint`) содержит правила зон и их исключения.

### Тарифы

Открытое ядро работает без сервера и без ограничений. На сервере команды у проекта есть тариф:
первые три месяца — Team для всех, затем Free (до трёх разработчиков, тестировщики не считаются)
или оплаченный Team. Кросс-аудит, проверка подписей коммитов, реестр исключений и аналитика —
только на Team.

- `beacon sync`, `beacon whoami` и `beacon checkpoints --team` показывают тариф: пробный период,
  оплату или лицензию, занятые места.
- `beacon audit start`, `beacon sign` и `beacon exception approve` на тарифе Free отказывают сразу,
  не дожидаясь ответа сервера. Проверяет и решает сервер: клиент лишь объясняет.
- Сервер сообщает минимальную версию клиента (`GET /api/v1/meta`); устаревший `beacon` получает
  предупреждение при `beacon sync`.

## Библиотека для сервера

Сервер команды не держит рабочих копий разработчиков: он хранит зеркала репозиториев и по каждой
ветке — снимок. Пакет экспортирует для этого библиотечный вход (`import … from
'project-vision-cli'`):

| Функция                          | Что делает                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------ |
| `collectSnapshot(root)`          | Снимок выгруженного коммита: файлы `.beacons/*`, индекс файлов, лог коммитов               |
| `indexView(snapshot)`            | То же, что `GET /api/index`: проект, состояние карты зон, индекс                           |
| `historyView(snapshot, today)`   | То же, что `GET /api/history`, на заданный день                                            |
| `timelineView(snapshots, today)` | Линии нескольких репозиториев на заданный день; битый план одной линии не прячет остальные |
| `todoFor(timeline, owner)`       | Личный список, как `GET /api/todo`                                                         |
| `parseCardBeacons(text)`         | Маяки карточки трекера: зоны и связь (задача, стопер, техдолг)                             |
| `dependencyView(snapshot)`       | Зависимости между зонами: сколько импортов ведёт из файлов одной в файлы другой            |
| `fileLinks(snapshot, file)`      | Зоны файла, другие файлы этих зон, его импорты и кто импортирует его                       |
| `registryView(snapshot)`         | Правила и исключения репозитория на коммите (`.beacons/rules.yml`, `exceptions.yml`)       |

Снимок несёт и импорты JavaScript/TypeScript-файлов, разрешённые до файлов репозитория:
относительные пути и алиасы `paths` из `tsconfig*.json` в корне. Из них и зон файлов получается
карта зависимостей модулей и связанные файлы код-вьюера.

Снимок переживает JSON: в нём сырые тексты карты, плана и настроек, а всё, что зависит от даты
(динамика, просрочка долгов, застой), считается из него в момент запроса. Проверок архитектуры в
снимке нет — они запускают инструменты проекта, а сервер код репозитория не исполняет.

| `beacon validate`                    | Проверка архитектуры инструментами проекта, код 1 при нарушениях               |
| `beacon checkpoints [--with <репо>]` | Линии чекпоинтов: пункты, стоперы, техдолг, застой                             |
| `beacon checkpoint tick\|close …`    | Ручная галочка; закрытие чекпоинта, условно — с техдолгом                      |
| `beacon debt close <чп> <долг>`      | Закрыть техдолг                                                                |
| `beacon todo [--owner email]`        | Мой техдолг (приоритетный первым) и незакрытые пункты                          |
| `beacon watch`                       | Держит индекс актуальным, перезапускает проверки архитектуры                   |
| `beacon serve [--port] [--origin]`   | Локальный API для дашборда с живыми обновлениями                               |
| `beacon mcp`                         | MCP-сервер для ИИ-агентов (stdio)                                              |
| `beacon hook <имя> [аргументы git]`  | Точки входа git-хуков: `prepare-commit-msg`, `commit-msg`, `pre-push`          |

Глобальная опция `-C <папка>` — работать с репозиторием в другой папке, как у git.

`beacon init` в проекте с husky дописывает вызовы в `.husky/*`, а не перезаписывает хуки; без
husky — ставит хуки в `.git/hooks`. Хук `pre-push` перепроверяет весь пушимый диапазон — на
случай коммитов через `--no-verify`.

## Несколько репозиториев

У каждого репозитория своя карта, ID зон согласуются вручную; `beacon check --with ../frontend`
показывает зоны, которые есть только с одной стороны. Локально линии нескольких репозиториев
собирает `beacon serve --with`, на сервере команды — проект: каждый его репозиторий становится
линией таймлайна.

## Что не входит в модуль 0

- Шапки во всех файлах зоны (`beacon sync`) — опция, появится по запросу.
- Подсказки нейросети для неразмеченных файлов при `init`.
- Плагин редактора — после модуля 1 (см. план).
